1. SIMPLE SUMMARY
-----------------

Better Routes is currently a Flutter application. Flutter allows one shared
application codebase to run on Android and iOS.

The main application code is written in Dart. Android and iOS contain the
platform-specific wrappers and configuration needed to launch Flutter.

The current application implements:

1. A splash screen
2. A welcome screen
3. Email/password login
4. Account registration
5. Google Sign-In
6. Password reset through Firebase

The map, route planning, route optimization, orders, drivers, and live
navigation shown in the workflow image are not implemented yet.

The current working flow is:

    App starts
        |
        v
    Firebase initializes
        |
        v
    Splash screen for 2.5 seconds
        |
        v
    Welcome screen
        |
        v
    Login or registration
        |
        v
    Firebase authentication message


2. TECHNOLOGIES AND LANGUAGES
-----------------------------

Main technology:
- Flutter

Main programming language:
- Dart

Platform/build languages:
- Kotlin for the Android entry point and Gradle configuration
- Swift for the iOS entry point
- XML for Android and iOS configuration
- Kotlin Gradle DSL for .gradle.kts files
- Generated C++, Objective-C, C, and platform files for desktop/mobile
  integration

The Android and iOS user interfaces are not separate implementations. Both
use the Flutter code in the lib directory.

4. CURRENT SOURCE FILES
-----------------------

lib/main.dart

This is the main Dart entry point. It:

- Ensures Flutter is ready
- Initializes Firebase
- Starts BetterRoutesApp
- Defines the application theme
- Defines the current welcome page
- Opens the authentication page when Get Started is pressed

lib/screens/splash_screen.dart

This file displays the BetterRoutes logo and slogan for 2.5 seconds. It then
opens the welcome page.

lib/screens/auth_screen.dart

This file contains:

- Login form
- Registration form
- Full-name field for registration
- Email validation
- Password validation
- Loading state
- Firebase email/password login
- Firebase account registration
- Google Sign-In
- Password reset email
- Firebase error messages

After successful authentication, the current code only displays a success
message. It does not yet open the map or an authenticated home page.

lib/pages/map_page.dart

This file exists but is empty. It is the intended place for the map page.

lib/firebase_options.dart

This file was generated by FlutterFire. It contains platform-specific Firebase
configuration for Android, iOS, macOS, web, and Windows.

test/widget_test.dart

This contains one small test. It checks that the main application widget can
be constructed. It does not currently test authentication, maps, routing,
location, drivers, or orders.

6. ANDROID FILES
----------------

android/app/src/main/kotlin/com/example/my_app/MainActivity.kt

This is the Android entry point. It extends FlutterActivity and starts the
Flutter application. It is intentionally very small because most behavior is
in Dart.

android/app/build.gradle.kts

This configures:

- Android application plugin
- Firebase Google Services plugin
- Flutter Gradle plugin
- Java 17
- Kotlin JVM 17
- Android application ID
- Debug and release builds

The current Android application ID is:

    com.example.my_app

This is still a default Flutter-style name. It should eventually be changed
to a permanent Better Routes ID, for example:

    com.betterroutes.app

If it is changed, Firebase must also be updated with the new Android package
name.

android/app/src/main/AndroidManifest.xml

This declares permissions for:

- Internet
- Approximate location
- Precise location

These permissions prepare the Android app for maps and GPS, but permission
handling still needs to be implemented in Dart.

android/app/google-services.json

This connects the Android app to the Firebase project. It currently identifies
the Android package as com.example.my_app.

android/settings.gradle.kts

This connects Gradle to the Flutter SDK and declares Android plugin versions.

android/build.gradle.kts

This configures Android repositories and build directories.

android/gradle.properties

This contains Android and Kotlin build settings. Kotlin incremental
compilation is currently disabled as a workaround for a Kotlin/Gradle issue.


7. IOS FILES
------------

ios/Runner/AppDelegate.swift

This starts Flutter on iOS and registers Flutter plugins.

ios/Runner/Info.plist

This contains iOS application metadata and launch configuration. It still
contains default names such as My App and my_app, which should eventually be

ios/GoogleService-Info.plist

This connects the iOS app to Firebase. The iOS Firebase bundle ID is:

The Android package is currently com.example.my_app. Android and iOS use
separate identifiers, but the final names should be chosen intentionally.

ios/Podfile

This configures CocoaPods dependencies for Flutter plugins.


8. FIREBASE STATUS
------------------

Firebase is currently used for:

- Application initialization
- Email/password authentication

- Password reset emails

There is currently no visible implementation for:

- Firestore
- Realtime Database
- Driver records
- Order records
- Route records
- Live location updates
- Driver assignment

Firebase API keys and application identifiers are present in the generated
configuration files. These are normally client configuration values, but they
should still be restricted through Firebase and Google Cloud settings.

11. RECOMMENDED NEXT STEPS
--------------------------

Phase 1: Clean up project identity

1. Rename the project from my_app to BetterRoutes.
2. Choose a permanent Android application ID.
3. Confirm the iOS bundle identifier.
4. Register the final Android and iOS IDs in Firebase.
5. Update the README with setup instructions.
6. Agree with your friend on branch ownership and merge rules.

Do this before adding many Firebase services. Changing application IDs later
creates additional configuration work.

Phase 2: Finish the authentication flow

After login or registration, navigate to a real authenticated home screen.

The intended startup logic should be:

    Splash screen
        |
        v
    Check FirebaseAuth.currentUser
        |
        +-- No user --------> Login screen
        |
        +-- Existing user --> Main app screen

Add tests for:

- Invalid email
- Incorrect password
- Registration
- Password reset
- Loading state
- Successful authentication
- Navigation after authentication

Phase 3: Build the first map MVP

1. Implement map_page.dart.
2. Request location permission with geolocator.
3. Check whether GPS is enabled.
4. Obtain the current device position.
5. Display an OpenStreetMap map with flutter_map.
6. Show the current user position.
7. Add OpenStreetMap attribution.
8. Add a button to recenter the map.

The first useful milestone should be:

    Login
        |
        v
    Authenticated home screen
        |
        v
    Map opens
        |
        v
    User sees current location

Phase 4: Add route planning

Add:

- Start location
- Destination location
- Additional stops
- Selected map markers
- Place search
- A route request model

A simple route request can contain:

    RouteRequest
        - start
        - destination
        - stops[]

Keep route planning separate from the map widget.

Phase 5: Add a routing service

OpenStreetMap provides map data, but it does not directly calculate routes
for the application. A routing engine is required, such as:

- OSRM
- GraphHopper
- Valhalla
- A hosted routing provider

The service should return:

- Distance
- Duration
- Route geometry
- Turn-by-turn information, if supported

Do not put private API credentials directly in Flutter source code.

Phase 6: Add the transportation backend

Choose a database/backend:

- Cloud Firestore
- Firebase Realtime Database
- A separate backend API

An initial Firebase-style structure could be:

    users/{userId}
    orders/{orderId}
    drivers/{driverId}
    routes/{routeId}

An order could contain:

    customerId
    driverId
    pickupLocation
    destinationLocation
    stops
    status
    createdAt
    updatedAt

Suggested order statuses:

    requested
    accepted
    driver_arriving
    in_progress
    completed
    cancelled

Phase 7: Build the driver workflow

    Driver login
        |
        v
    See available orders
        |
        v
    Accept an order
        |
        v
    Navigate to pickup
        |
        v
    Start trip
        |
        v
    Send location updates
        |
        v
    Complete trip

Customer and driver screens can share data models, but they should have
separate user interfaces and permissions.

Phase 8: Add route optimization

Implement optimization only after basic route requests and order tracking
work correctly.

For example:

    Pickup
        |
        v
    Stop A
        |
        v
    Stop B
        |
        v
    Destination

The optimization logic should be separate from the Flutter UI so it can be
tested independently.
